Alec has shown the product, so I'll focus on what happens behind the AI part. Read this diagram from left to right. The first AI call breaks the original problem into concepts and creates the first probe pair. Later pairs are generated as the student moves through the session. Code checks the format, and a separate AI call can review the content against the original problem. The architecture we're aiming for makes that review automatic after generation. The checker itself is built, but connecting it automatically is still work to do. This diagram is the intended flow with API access, not a claim that we've run it.

Leading models score highly on mathematics.

Speaker script

The reason we think AI is a reasonable tool here is that mathematical reasoning has become a genuine strength of leading models. DeepSeek's R1 paper reports 97.3 percent on MATH-500, a benchmark drawn from competition mathematics.

One part of its training uses rewards for getting mathematical answers right. That gives the training process a concrete correctness signal, rather than only rewarding an answer that sounds convincing.

This is strong evidence that models can solve challenging mathematics. What it doesn't tell us is whether every question our application generates is correct, clearly worded, or useful for diagnosing a student's understanding. Those are the parts we still need to evaluate.

A couple of details if someone asks: this is reported pass@1, not the chance of getting at least one correct answer in 64 attempts. The authors describe sampling 64 responses per query to estimate pass@1 where sampling is required. MATH-500 is not an Ontario curriculum assessment, and this result belongs to DeepSeek-R1, not the Claude model our application uses. We aren't claiming that AI outperforms every high-school student.

The checker gets the problem, not just the answer key.

Speaker script

The checker isn't just asked whether the output looks good. It gets the original problem and the generated material, then uses a checklist. For the breakdown, it looks for missing or unnecessary prerequisites. For the probes, it checks the answer key, options, concept match, explanation, hint and retry difficulty. Here's an example: if the generator marks two x plus three as the expansion of two times x plus three, the checker should flag the answer key because the correct result is two x plus six. That's the behaviour we want to measure, not a result we're claiming. It returns findings; it doesn't automatically rewrite the question.

Research on AI judges helps explain that design choice. Thakur and colleagues found differences from human ratings, including leniency and prompt sensitivity. Yamauchi and colleagues found that clear criteria mattered. That supports using a specific checklist and checking the reviewer's decisions against human-reviewed examples. It doesn't prove that our reviewer is reliable. It uses the same provider as the generator, so it can share the same blind spots.

Tools can help us measure and improve.

Speaker script

We wouldn't need to build all the evaluation infrastructure ourselves. There are established tools for running examples repeatedly and comparing the results.

With Mathify, we could feed the same problems through different versions of the generation prompt. We'd check whether the answers are correct, whether the probes target the intended concept, and whether the reviewer catches mistakes.

LangSmith could help us inspect the individual calls and compare runs. promptfoo could repeat a set of examples with automated checks. DeepEval could organize evaluation tests and scoring criteria.

The tools don't improve accuracy just by being there. They help us identify failures and find out whether a prompt or model change actually improves the result. These are available options, not three tools we're proposing to install together, and none is currently integrated into Mathify. If we use an AI judge for scoring, its ratings still need to be checked against qualified human review.

Mathify examples could ground our evaluation.

Speaker script

A useful next step would be a set of examples from Mathify, if they're able to provide one. Ideally, that would include real curriculum-style problems, reviewed breakdowns, and examples of good probing-question pairs.

That would let us evaluate against the work this product actually needs to do, rather than relying only on general maths benchmarks. We wouldn't require the AI to copy the reference question word for word. We'd check whether its alternative is mathematically correct and tests the right concept.

We could also compare generation with review enabled and disabled, then measure whether the checker catches meaningful errors and how often it flags good material. We don't currently have those results or tutor responses, so this is a proposed validation route, not a completed study.

Any supplied examples would be candidate reference material until qualified reviewers confirm their correctness and suitability. We'd keep some examples held out for final evaluation rather than tuning against the whole set. If examples come from student interactions, we'd need permission and de-identified material. Valid alternative solutions and probes should count, not just exact text matches. Our existing small test runner is a starting point, not a substitute for that review.

Research and implementation references.

Speaker script

Here's where the evidence comes from. DeepSeek's paper gives us a published result for mathematical solving. The AI-judge papers inform how we design the review step, including why we need clear criteria and human checks. The tool documentation shows what is available for running evaluations; it isn't evidence that we've already used those tools.

The overall pitch is that published results show strong mathematical capability, a review layer gives us another opportunity to catch errors, and reviewed Mathify examples could tell us how well our particular system performs. We haven't measured that accuracy yet, and we still have no tutor questionnaire responses.

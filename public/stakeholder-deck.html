A clearer starting point for tutoring.

Speaker script

The idea is to make the start of a tutoring session more useful. A student's question tells us what they're working on, but it doesn't always tell us where they're stuck. Mathify uses the waiting time to ask short concept questions, then puts those answers in a brief the tutor can inspect. Today I'll walk through one example, explain why the approach is worth testing, and show exactly which evidence we have and which evidence is still missing.

The question shows the task. It does not show the gap.

Speaker script

Take this equation. The student might be stuck on brackets, balancing, or dividing at the end. Looking at the question alone doesn't distinguish those possibilities. A short probe can give the tutor something more specific to discuss. It still isn't a diagnosis: a wrong choice could be a slip or a guess. We're trying to surface a useful starting point that the tutor confirms with the student, while leaving the whiteboard available for their own work.

Check understanding before choosing the feedback.

Speaker script

This is the strongest educational reason for the design. The EEF's feedback guidance recommends using formative assessment to establish learning gaps before giving feedback. We've translated that into a simple sequence: ask about a concept, inspect the response, and let the tutor decide where to begin. The research supports that principle. It does not evaluate Mathify, and it doesn't establish that our AI questions are accurate or that this brief saves tutor time. Those are separate things we need to measure.

One problem becomes a traceable tutor handoff.

Speaker script

The student submits a problem, and the AI breaks it into ordered concepts. For each concept, the app asks a main probe and has an easier retry ready. A wrong answer or 'I don't know' leads to that retry. The brief keeps the actual responses, including early submission and concepts that weren't reached. The tutor can inspect the gap rather than trust an unexplained summary. Whiteboard work travels with the handoff as an image preview; the current AI does not assess that handwriting.

A missed bracket question leads to a simpler check.

Speaker script

Here's the same example all the way through. The main probe asks the student to expand 2 times x plus 3. They choose 2x plus 3, which misses multiplying the second term. The easier question asks about 2 times x plus 1, and they choose the correct 2x plus 2. That suggests a simpler example may be a useful starting point, but the tutor should check their thinking. This is a synthetic walkthrough, not an actual student or live-model accuracy result.

Put the useful detail first.

Speaker script

This is the priority card in the working tutor view. The possible gap comes first. The tutor can compare the selected answer with the key, and see that the student got the easier retry right. That supports a specific conversation about how multiplication applies to both terms. It doesn't mean the student has a confirmed misconception. The confidence label elsewhere in the brief is also a heuristic, not calibrated accuracy. Our next usability check is whether tutors can read this quickly and interpret it correctly.

A second AI check helps. It is not ground truth.

Speaker script

There are different kinds of checks, and they answer different questions. Schema validation checks that the response has a usable structure. The optional second AI call reviews the breakdown and the probes, including the easier question's hint and explanation. But two calls to the same provider can agree on a mistake. An independent mathematical and educator review is still needed. We have reference answers and a harness to start that work, but we haven't run a live accuracy benchmark. No live-model accuracy percentage is claimed.

The workflow is tested. Effectiveness is still unmeasured.

Speaker script

Here's the boundary of what we've verified. The offline suite has 111 passing tests, and three browser checks cover the synthetic handoff flows and the presentation. Eight reference solutions have also been checked. These numbers tell us about software behavior and reference mathematics, not the quality of 111 generated questions or outcomes for 111 students. Live probe correctness, tutor comprehension, and student benefit remain unmeasured.

The questionnaire is out. The responses are still pending.

Speaker script

There are zero tutor responses so far, so there's no tutor feedback analysis to present yet. The external questionnaire has been distributed and is intended to tell us about tutors' needs and layout preferences. This in-app form asks about an individual report: usefulness, breakdown accuracy, and probe quality. We checked the submission path and fixed the false-success behavior on failed saves. Once responses arrive, we'll report the count, rating distributions, and comments without overgeneralizing a small sample. A timed walkthrough will complement those opinions with observed behavior.

Validate correctness, then test usefulness.

Speaker script

I'd validate this in stages. First, generate live items for the existing reference cases and have a reviewer check the concepts, answer keys, distractors, hints, and retries. Record the number reviewed and the errors, rather than just an overall success claim. Then give tutors matched synthetic cases with and without the brief, counterbalancing which one they see first. Measure time to the main takeaway and whether that takeaway is correct, alongside their feedback. A small student pilot should follow only if the mathematical and tutor-review gates are met.

A tutor-reviewed demo, not another feature sprint.

Speaker script

The next milestone I'd ask us to approve is a small validation round. We need live-model access, someone to independently review the mathematics, and tutors for a short walkthrough. Alec already put the breakdown, reviewer, evaluation harness, and survey scaffolding in place. The work in this session extends the whiteboard, makes feedback saving reliable, and makes the evidence and handoff easier to inspect. The remaining question isn't whether we can build more screens. It's whether tutors get a correct, useful starting point from this one.

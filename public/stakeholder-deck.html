A focused tutor handoff starts with one problem.

Speaker script

Mathify takes a student's math problem and prepares a short handoff for a tutor. The goal is to make it easier to choose a useful first question. That is the product promise, not a proven improvement in learning or tutor time. I will give a quick refresher on the workflow, then focus on the harder question: how do we know the AI-generated material is correct?

Question in. Evidence out.

Speaker script

The student submits a question, Mathify breaks it into prerequisite concepts, and it generates a main probe plus an easier retry for each step. A wrong or unsure response can lead to that retry. The answers and any whiteboard work are retained in a tutor brief. This is a refresher of the workflow only; the rest of the presentation is about the reliability of the generated content.

How can we trust each AI-written probe?

Speaker script

In this synthetic example, the student misses the main distribution question and gets the easier retry correct. That gives the tutor a possible place to start, not a confirmed diagnosis. More importantly for this presentation, both questions and their answer keys are AI-generated in the real workflow. A polished report is only trustworthy if those underlying pieces are right. The rest of the talk is about what is checked, what we can measure, and what remains unknown.

Valid structure does not prove correct maths.

Speaker script

The generator has useful engineering checks. It must return the expected fields, a plan of three to five steps, a breakdown of two to six steps, and four option IDs A through D with a key ID that exists. Those checks catch malformed output. They do not prove the marked answer is mathematically correct, that only one choice is right, that distractors diagnose a misconception, or that a hint does not reveal the answer. Structure is a gate, not evidence of correctness.

A second AI can flag issues. It cannot certify correctness.

Speaker script

There is a second AI review path for the breakdown and generated probes. Its rubric now checks prerequisites, answer keys, distractors, concept alignment, explanations, hints, and whether the retry is simpler while testing the same concept. It is optional and disabled by default, not an automatic student-flow safeguard. It also uses the same provider as generation, so both calls may share the same blind spots. We should treat its findings as review signals, not ground truth.

AI judges need checks against people.

Speaker script

The research changes how confidently we should interpret a second AI opinion. Thakur and colleagues found that judge models can differ from human ratings, with sensitivity to prompt complexity and a tendency toward leniency. Yamauchi and colleagues found that clear evaluation criteria matter, while chain-of-thought added little when criteria were already clear. A 2026 education study compared expert-validated AI and human multiple-choice questions in one Operating Systems course with 42 students; that is bounded evidence in a different subject, not proof about Mathify's math probes. The takeaway is not that AI questions are unusable. It is that rubric-based, human-checked evaluation is necessary.

Ten fixtures separate misses from false alarms.

Speaker script

The checker benchmark is now implemented. It sends two unmodified fixture controls and eight cases with one planted fault each: missing or unrelated prerequisites, a wrong key, ambiguous options, a concept mismatch, a wrong explanation, a leaking hint, or an easier question that is not easier. The report separates per-category fault detection, flags on completed controls, unclassified findings, and API failures. This is a small exploratory harness, not a representative reliability study; the fixture itself still needs an independent educator review.

No live checker result yet.

Speaker script

I attempted to move from harness design to a live checker result. This environment has no Anthropic API key configured, so I did not send any benchmark calls. That is an access blocker, not a successful or failed model evaluation. The benchmark refuses to run in mock mode, because the mock checker always returns an empty issue list. The implementation and offline scoring tests can be verified here, but we must not present them as evidence of live checker reliability.

Every generated probe pair is now retained.

Speaker script

The generation harness now keeps the full analysis and every planned main/easier pair across the eight project-authored examples. It records follow-up call latency and failures separately from the analysis call. Topic matching and breakdown length remain sanity checks only. The harness does not decide whether the math, answer key, distractors, concept mapping, hint, or retry is good. A math educator must score those artifacts independently, and a live run still requires credentials.

Software checks are not AI accuracy evidence.

Speaker script

Here is what we can say today. Offline tests verify software behavior, and eight authored reference problems have checked solutions. There are zero live checker benchmark results and zero tutor questionnaire responses. The report confidence label is a deterministic heuristic based on answer patterns and completion, not an AI confidence score or a calibrated probability that the report is accurate. Before making an accuracy claim, we need a live sample, independent math review, and tutor review. Until then, effectiveness remains unknown.

For reference, the checked answers are x = 4; (x + 2)(x + 3); hypotenuse 5 cm; sin θ = 5/13; 5 cups; (x, y) = (2, 5); circle area 153.9 cm²; x⁴; x ≠ 0. These solve the fixed examples. They are not generated-model results.
